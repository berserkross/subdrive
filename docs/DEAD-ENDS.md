# SubDrive 死路记录

试过、失败或明确放弃的方案。新会话动手前先读这一页，能省掉重复踩坑的时间。

## 排查

- **「下载失败 → 直接改 `_serve_file()` / 放开下载鉴权」**
  尝试了什么：把问题定位在 `_serve_file()`（约第 717 行）与 `storage.download_iter()`，并考虑放宽下载接口鉴权让 `<a>`/`window.open()` 能直接打开。
  失败原因：报障表述是「下载无法开始」，请求可能根本没发出；`_serve_file()` 在真正传输前就写了 `download: ok` 审计，所以「日志显示成功」不能证明文件传完；而且仓库版本的前端下载函数确实带了 `Authorization`，「漏传凭证」的假设不成立。
  结论：先看浏览器是否真的发出了 `/api/files/download`，再按状态码分支（无请求 / 401 / 4xx / 一直 pending / 5xx / 200 但没保存）。鉴权只收紧。

- **「用首页恢复正常来归因 502」**
  尝试了什么：把 502 归到某个具体原因——启动 ping Seafile 失败、compose 端口映射与代理不一致、线上仍是旧镜像。
  失败原因：没有故障当时的日志，四条候选都无法区分；首页恢复之后更无法回溯是哪一层出错。
  结论：这次 502 的归因保持「未知」。恢复访问只能说明现在能访问，不能说明原因已被消除。

- **「只改前端 `await resp.blob()` 就修好下载」**
  尝试了什么：把 blob 保存方式列为首要修复点。
  失败原因：它只能解释「看不到下载任务」，解释不了 502；502 属于入口层，与前端保存逻辑无关。
  结论：分层定位后各修各的——体验问题改前端四态与取消，502 查服务端与代理。

- **「凭公开登录页判断前端质量」**
  尝试了什么：在没有 `static/` 源码、也没有登录后界面的情况下评价前端。
  失败原因：登录页显示正常不代表下载逻辑、文件名编码、`innerHTML` 渲染与登录态处理正确，把两件事混为一谈会给出错误结论。
  结论：前端结论只能来自 `static/` 源码 + 一次真实的失败请求记录。

## 部署

- **「推到 GitHub 就等于线上更新」**
  尝试了什么：以仓库 main 上已修好的 Seafile 下载地址解析，解释线上故障已解决。
  失败原因：Dockerfile 把源码 COPY 进镜像；上传 GitHub 不触发构建、不重启容器、不替换线上镜像。
  结论：先 `git rev-parse --short HEAD` 与容器实际版本对齐，再谈「已修复」。

- **「在项目根目录放 `.env` 就能切到 live 模式」**
  尝试了什么：打算靠项目目录的 `.env` 覆盖 compose 里写死的 `SEAFILE_MODE: "stub"`。
  失败原因：Docker 区分用于配置插值的 `.env` 与用于容器环境的 `env_file`；仓库 compose 没有 `env_file`，也没有把三个 Seafile 变量用 `${...}` 映射进去，容器内根本看不到它们。
  结论：切 live 必须改 compose 显式传环境变量；排查要看「容器实际运行配置」，不要只看 `.env` 文件。线上是否另有覆盖配置仍未确认。

- **「加 uvicorn workers 解决并发与配额超卖」**
  尝试了什么：曾考虑直接照搬多 worker 部署来提吞吐，并顺带解决并发注册与并发上传突破配额（未实施）。
  失败原因：`threading.Lock` 只协调同进程线程；数据库、管理员目录与校准线程都在模块导入期初始化，多 worker 会重复调度；配额检查/写入/记账本身不是原子操作。
  结论：先做事务内原子占用、容量预占与单调度者，再谈 workers。

- **「把『服务端每次读 1 MiB』当成分片上传/断点续传」**
  尝试了什么：用现有上传循环说明已具备断点续传基础。
  失败原因：那只是服务端读取文件的分块，客户端没有可恢复的上传会话，中断后只能整份重传。
  结论：分片上传与断点续传是独立需求，不能写进已有能力，也不能写进海报。

## 功能边界

- **「用『加密文件夹』满足带提取码的对外分享」**
  尝试了什么：把「半外部（有密码/密钥）分享」需求挂到现有加密文件夹上。
  失败原因：加密文件夹是个人文件的静态加密，不是受控分享——没有外部访问者、有效期、撤销、访问审计这些语义。
  结论：受控分享作为独立需求另做，先定义权限、有效期与撤销规则。

- **「把会话 token 放进 URL 以便下载或预览」**
  尝试了什么：用 `?token=...` 让 `<a>`、`window.open()` 这类不能带头的请求也能下载。
  失败原因：`extract_token()` 确实接受 URL 参数 token，于是凭证会进入访问日志、代理日志与 Referer，且无法单独撤销。
  结论：不做。改短时、限定文件用途的下载票据，或受保护的 Cookie 会话。

- **「按通用网盘功能清单继续堆功能」**
  尝试了什么：以「功能越全越专业」为方向继续扩展通用网盘能力。
  失败原因：无法验证社团是否真的会用起来；而可靠性（注册并发、权限保护、配额原子性）与交片/选片流程才是决定留存的环节。
  结论：放弃按功能清单推进。下一版以「能稳定交片、能快速选片、误操作能恢复」为目标验收。
