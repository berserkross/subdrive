# SubDrive 决策记录

只记录已敲定的技术/产品决策及其理由。理由缺失的决策迟早会被重新推翻，因此每条都必须带「为什么」。

## 路线与产品

- **D1 沿用现有技术栈，不推倒重来**｜继续 FastAPI + 原生 JS 单页前端 + `app/storage.py` 存储适配层。
  为什么：后端已覆盖邀请码注册、会话撤销、容量配额、审计、Range 下载等成品级能力，属可继续发展的基础；SQLite 换不换取决于实际写入压力与部署方式，眼下更急的是事务、锁与任务执行方式；前端没有仅为了「更专业」就换框架的必要。

- **D2 在个人空间之外新增「活动资料库」，两者并存**｜不把现有个人目录改造成公共目录。
  为什么：现有表结构与路径逻辑是「每人一个私人目录」，适合个人存储；摄影社团的真实流程是「建活动 → 多人交片 → 负责人选片 → 上传成片 → 归档」。共享权限必须先于共享入口做好，否则误删与素材归属会立刻成为问题。

- **D3 三层角色模型**｜成员可上传、默认只能修改自己的文件；负责人可整理与选片；管理员管理空间。
  为什么：交片场景里素材归属必须清晰。不同相机都会生成 `DSC_0001.JPG`，多人交片时必须保留上传者身份、明确同名策略，不能静默覆盖。

- **D4 选片状态第一版只做三态**｜`待选 / 入选 / 成片`，暂不做复杂审核流。
  为什么：先用最薄的状态机验证「社员能稳定交片、负责人能快速选片」这个价值假设，流程复杂度等真实使用后再加。

- **D5 下一版的验收目标是行为目标，不是功能清单**｜「社员能稳定交片，负责人能快速选片，误操作能够恢复」。
  为什么：继续堆通用网盘功能无法验证项目价值，这三个行为才是社团留不留下来使用的判据。

## 正确性与并发

- **D6 邀请码消耗必须在数据库事务内原子占用**｜并处理建目录失败后的补偿。
  为什么：已本地复现——一个只能用一次的邀请码被两个并发注册同时使用成功，计数最后仍是 1。检查与扣减分两段且中间释放了锁。

- **D7 注册失败必须清理已创建的用户记录，异常类型必须先用对**｜修复 `StorageConflict` 未定义问题。
  为什么：复现时抛 `NameError`，并且失败后残留用户记录，留下半完成状态，后续清理由此变成人工操作。

- **D8 账号禁用必须保护所有者、操作者自身与最后一个可用管理员**｜三条保护同时生效。
  为什么：取消管理员权限有保护、禁用账号却没有，导致普通管理员可以禁用所有者，也可以把自己或最后一个可登录管理员锁在门外。

- **D9 正式部署只允许显式初始化管理员**｜不允许空库首个注册者自动成为管理员。
  为什么：新部署、数据库丢失或路径配置错误都会把系统重新带回「抢注管理员」状态，这是可被外部触发的提权路径。

- **D10 容量记账改为「预占 → 完成结算 → 失败释放」**｜不接受「先检查、再写入、后记账」。
  为什么：配额检查、存储写入、容量记账三步不原子，多进程并发上传会突破配额；校准线程与上传交错还会互相覆盖计数。

- **D11 `threading.Lock` 不作为并发保障**｜多 worker 化必须等事务边界与后台调度理顺之后再做。
  为什么：进程内锁只能协调同进程线程；而且数据库、管理员与校准线程都在模块导入期初始化，多 worker 会重复调度。单纯加 workers 不会修好这些问题，只会让它们更难复现。

- **D12 多步写入要有显式事务边界，启动副作用要移出导入期**｜注册、邀请码消耗、权限变更各自成事务；数据库/管理员/后台线程改由明确的应用启动流程创建。
  为什么：数据库自动提交时，这些业务动作本来就没有整体事务保障；导入期副作用让启动顺序不可控，也让失败无法被捕获和报告。

- **D13 启动路径上的异常不许静默吞掉**｜禁止 `except Exception: pass`。
  为什么：容量校准与管理员目录初始化现在会吞异常，长期失败也无人发现，最后表现为「配额莫名其妙不对」这种无法定位的现象。

## 安全

- **D14 不用长期登录 token 充当文件链接凭证**｜对外链接走短时、限定用途的下载票据，或受保护的 Cookie 会话。
  为什么：URL 里的 token 会落进访问日志、代理日志与 Referer；而前端下载本来就带 `Authorization`，这条路径没有必要存在。

- **D15 预览按白名单限制内容类型，主动内容不做同源 inline**｜HTML/SVG 等隔离或以附件形式返回。
  为什么：`_mime_for()` 会把 HTML 推断成 `text/html` 再以 `inline` 返回，同源主动内容存在脚本执行风险；上传内容里的活动脚本本就是已知攻击面，文件服务应与应用隔离。

- **D16 下载鉴权只收紧，不放松**｜不通过取消或绕过下载接口鉴权来「修」下载失败。
  为什么：文件列表与上传正常而下载打不开，典型原因是下载路径没带凭证；取消鉴权等于把整个文件树公开。

## 存储与传输

- **D17 Seafile 下载地址解析必须同时兼容两种返回**｜`302 + Location` 与 `200 + JSON 字符串形式的地址`。
  为什么：旧实现只认 302，真实服务返回 200+JSON 时报「Seafile 未返回下载地址」并冒泡成 502。已补回归测试覆盖两种形式与 Range 下载。

- **D18 「服务端每次读 1 MiB」不是断点续传**｜上传会话/分片/恢复作为独立需求另做，不写进已有能力清单。
  为什么：那只是服务端读取文件的分块，客户端没有可恢复的上传会话；把两者混为一谈会让「RAW 和视频较大、网络易断」这个真实痛点看起来已经解决。

- **D19 下载界面必须显示连接中/接收中/失败/已保存四态，并可取消**｜不接受收完整个文件才触发保存的隐式体验。
  为什么：`await resp.blob()` 收满整个文件才创建链接，浏览器没有原生下载任务，大文件时用户会认为「下载没开始」；而这正是最初报障的表述。

- **D20 前端错误提示优先解析 `detail.message`，再退回顶层 `message`**｜最后才用 `下载失败（HTTP <code>）`。
  为什么：存储层异常返回的是顶层 `message`，前端只读 `detail.message`，真实的 Seafile 错误被压成笼统的「下载失败」，让排查每次都从头开始。

- **D21 缩略图与元数据提取交给后台任务**｜原片保留，另生成适合网页浏览的预览图。
  为什么：EXIF/缩略图同步生成会阻塞上传；RAW 原片也不适合直接网页浏览。

- **D22 前端与 API 同域，由同一个 FastAPI 服务提供**｜初期不拆两个域名。
  为什么：同域最简单，拆分只会额外引入跨域、Cookie 与凭证处理问题，与眼下要解决的可靠性问题无关。

- **D23 阻塞型存储调用不得直接在 `async def` 里执行**｜改走线程池或异步客户端。
  为什么：FastAPI 不会自动把普通同步辅助函数放进线程池；存储适配层一旦做阻塞网络调用，就会阻塞整个事件循环，上传期间全站变慢。

## 运维

- **D24 GitHub 仓库、运行中的服务、用户数据是三个分别管理的部分**｜任何「已修复」的判断都要先确认线上运行的提交或镜像。
  为什么：Dockerfile 把源码 COPY 进镜像，上传 GitHub 不会构建、不会重启、不会替换容器。否则会把「仓库里已修的版本」和「线上旧镜像」混为一谈。

- **D25 备份必须同时覆盖应用数据库与 Seafile 侧数据，并做恢复演练**｜容器部署时两者都要落在持久化卷。
  为什么：SQLite 保存「谁是谁、谁能做什么」，Seafile 保存文件本体，只备份一部分不能恢复网站；未演练过的备份不能算备份。

## 文件与覆盖

- **D26 同名冲突用目录隔离解决：`活动名/用户名/`，不改名、不报错**｜上传落点按上传者身份分段，而不是给文件加序号或让请求失败。
  为什么：改了序号就丢失原文件名（摄影社团交片时文件名本身是信息）；报 409 会打断多人同时交片；分目录保住 D3 的「保留上传者身份」，也让记账有明确归属。
  落地形态（按 D27 定稿）：**写自己的目录直接落根**；**写别人的共享目录，自动落到该目录下以自己用户名命名的子目录**（`/alice/春游/bob/DSC_0001.JPG`）。
  边界：个人空间内同一个人覆盖自己的同名文件仍静默发生（同一所有者自身覆盖，暂按可接受处理）。
  被否方案：自动改名 `DSC_0001 (2).JPG`（丢原名语义、目录变脏）；报 409（打断批量交片）。

- **D27 共享以「文件夹」为授权单元，创建即永久共享，名单可改，配额算上传者**｜个人空间里的目录默认私密；用户可以把某个文件夹创建为「共享文件夹」，创建时选授权成员，之后随时增删名单，但**不能降级回普通文件夹**。
  为什么：把文件夹当授权单元，用户已有的心智模型直接可用，不需要「活动」这层中间概念和一个管理界面；配额算上传者（B 传 1MB 进 A 的目录，扣 B 的额度）让人人受自己的配额约束，共享目录总量天然有界，不需要再造一个「共享容量上限」。
  权限：授权成员可查看、下载、上传；**删除只能由上传者本人执行**（谁传的谁删，配额回冲天然正确，不必记录贡献者）。未授权者一律看不到该目录。
  风险（已知，实现时必须处理）：Seafile 目录没有 ID、只有路径，授权记录存的是路径前缀，所以 **`rename` / `move` 必须和授权表在同一事务里一起改**，否则权限会静默失配。
  被否方案：给共享空间单独设总容量上限（配额按上传者后已无必要）；只读共享（成员之间无法互相交片）；Seafile 自带共享（所有用户共用一个 token，Seafile 不认识我们的用户）。

- **D28 共享落地时的四条实现决定**｜D27 只定了权限模型，这四条是写代码时才必须拍板的细节，均已落地并有回归。
  1. **落点强制化**：写别人的共享目录时，服务端把请求路径改写成 `<共享目录>/<自己用户名>/` 再交给存储层，前端给什么路径都不改变落点。这样「只能删自己传的」和「跨人同名」两头都由目录结构保证，不需要一张文件归属表。
  2. **覆盖写按 `stored - prior` 记账**：`storage.upload()` 是 `wb` 截断，旧版本在磁盘上消失，若照旧记全量就会让配额虚高、直到管理员校准。改成先 `stat` 旧大小再记增量，响应带 `replaced: true`。这同时修正了 `tests/test_features.py` F1 原来「覆盖写记两份」的断言——那条断言编码的是缺陷，不是契约。
  3. **共享目录及其上级禁止 `rename` / `move` / `delete`**：Seafile 目录只有路径没有 ID，改名会让授权记录静默失配；改由「取消共享」而不是删除来收场，别人传进来的文件才不会连带消失。返回 `shared_rename` / `shared_move` / `shared_delete`。
  4. **授权只覆盖被共享的那一个目录，不含上级**：`/api/files/list?owner=` 只能从被授权前缀往下走，看不到对方的根目录，前端入口走 `/api/shared/list`。少一层「上级可见性」就少一条越权面。
  未做：共享目录整体的容量预占、Seafile 侧 ACL。（前端入口已于 `1298d14` 落地，见 D29。）

- **D29 成员可以管理自己那一格里的东西，但那一格本身不能改名/移动**｜补 D27 没覆盖到的一半：成员在共享目录里对自己传的文件和目录可以改名、移动、删除（前端从「一律不给按钮」改成「进到自己那一格才给」）。`<共享目录>/…/<我的用户名>/` 这个文件夹本身禁止 `rename` / `move`（`400 cell_rename` / `cell_move`），因为它的名字就是归属标记，改了随后上传的落点就算错。
  为什么选「能管自己的」：文件是成员自己传的，传错了要能自己收拾，否则每次都得找创建者。
  顺带修掉一处既存越权：`files_rename` 原先没有按 `write=True` 解析，任何人只要知道路径就能改共享目录里别人的文件名（实测返回 200）。改名从此与上传、删除同一条归属规则。
  判断用的是「路径最后一段 == 本人用户名」这一字面规则，所以自己那一格里若真有同名文件也会被 400 拦住；要精确区分得再查 `storage.stat`，暂不做。
  未做：成员删除「自己那一格整个文件夹」目前仍允许（会连带删掉自己传的东西），是否禁止待定。

- **D30 落点判定用「共享根 + 用户名」当锚点，不用「路径里出现过用户名」**｜D28 第 1 条只说了「强制改写落点」，没说「已在格内时不要重复追加」，于是成员在 `<共享目录>/…/<我>/子目录` 里上传会得到 `…/<我>/子目录/<我>/<文件>`，多套一层。
  为什么不用字面规则：创建者若恰好有个与成员同名的目录（`公共资料/bob`）并共享给他，字面规则会把他的上传落到**共享根**上，正是 D27 要拦的那件事。
  落地形态：`_cell_rel(user, owner_name, path_raw)` 先求 base，若 `base == <共享根>/<我>` 或在其之下则原样返回，否则补一层用户名；出口统一再过一次 `write=True` 校验，不绕过 `_foreign_target`。上传与建夹共用这一份逻辑。

- **D31 只有管理员能创建共享文件夹**（B1，用户拍板）｜D27 原本允许任何成员把自己名下的目录共享出去，等于人人有权开「公开目录」。收口后 `POST /api/shared/create` 走 `require_admin`（非管理员 `403 admin_required`），前端对非管理员隐藏「共享此文件夹 / 管理共享 / 取消共享」按钮。
  为什么：公开目录是全局性动作（决定哪些内容对外可见、占用谁的配额），留给管理员把关；成员在已授权目录里的读写能力完全不受影响。
  注意：`shared_members`（名单管理）仍由创建者（现必为管理员）操作；D27「创建即永久共享、名单可改」其余部分不变。
  待办：B6 将引入「文件夹管理员」角色，届时创建权限与名单管理权限按新矩阵再核一遍。

- **D32 名单留空＝全员，在「读取时」解释，不在创建时快照**（浏览器 e2e 抓出来的）｜D27 写的是「留空＝所有注册成员可见」，实现却是把名单落成 `shared_grants` 行：留空＝零行＝谁都不许进。创建者建共享时通常还没有别的用户，于是「全员可见」的目录实际只有创建者自己看得到；后来注册的人也永远拿不到授权。
  改法：`_share_roots_of()` 与 `shared_list` 的「被授权」分支都改成 `NOT EXISTS(授权行) OR EXISTS(我的授权行)`——零行解释成「全员」，非零行仍按名单，收窄时立即生效（原 S6 用例改成分三种情况逐条断言，54 → 56 项）。
  为什么不做「创建时快照全员 + 每次注册补授权行」：那要把「谁算全员」写进数据，之后禁用/新增用户都得回填，是第二份真相。
  顺带修掉 `static/app.js` 的 `enterShared()`：非本人共享目录原先 `curPath = ""`，于是被授权者点进去其实在列**对方的根目录**（403），上传也落不到共享目录。改成 `curPath = f.path`。
  这两个 bug 后端测试都测不到——它测的是 API，不是「点了能不能用」。从此第 7 道门：`tests/e2e/test_e2e_browser.py`（26 项）。

- **D32 附：e2e 不进主门禁，但发版前必须真跑**｜`tests/e2e/test_e2e_browser.py` 需要额外装 `playwright`（用本机 Chrome，不下载浏览器），装不上时打印 `[SKIP]` 并 exit 0，免得改前端的人被一个 150MB 依赖卡住；但打包发版前必须看到全绿 PASS，它是「页面真能用」的唯一证据。

- **D33 批量操作＝前端串行循环，不新增后端路由；只做下载/移动/删除三件套**｜用户拍板的交互参考 Win11：行首常驻复选框 + 表头全选（部分选时 `indeterminate`）+ 勾选后底部浮出操作条（下载/移动/删除/取消）。zip 打包明确不做。
  为什么不加 `/api/files/batch-*` 这类批量端点：一个请求做多件事就要定义部分成功的返回语义、幂等与回滚，而这三件本身就是逐文件独立操作；前端循环 + 逐项报数（`已删除 N 项，M 项失败：<第一个失败原因>`）语义更简单，也不用新增授权面——每一条仍过原有的门。
  为什么多文件下载串行：浏览器对多文件下载会为每个文件弹一次保存框，并发反而更容易被拦；选中的文件夹跳过并提示个数。zip 需要一条流式压缩路由（遍历 + `zipfile` 边压边发）加配额与限流考量，等真有需求再做。
  为什么勾选状态只活一次刷新：`refreshList()` 里 `selected.clear()`——否则切目录后旧路径还留在集合里，批量删除会删到「看不见的东西」，这是最容易变成事故的状态残留。

- **D34 覆盖写先问一声：前端三选一 + 服务端按 `expected_old_size` 复核**｜同名文件上传不再静默覆盖。前端在传之前先 `GET /api/files/detail` 探一次同名文件（404 就照常传），探到就弹「已经有同名文件：X（8.2 MB，昨天 14:03）」+ 替换 / 两者都保留 / 跳过。
  为什么要有服务端复核：弹窗给用户看的是「你即将替换掉那个 8.2 MB 的文件」，这个前提必须在落盘那一刻仍然成立；期间被别人改过还照覆盖，就是拿用户没看过的内容替用户做决定。所以替换时带 `expected_old_size=<旧大小>`，服务端比对不一致 → `409 conflict`，不落盘，记一条 `denied` 审计。前端探测是尽力而为，服务端 409 才是兜底——两者是「体验 + 保险」的关系，不是二选一。
  「两者都保留」= `on_conflict=rename`，服务端 `_dedup_name()` 在同目录里挑 `X (2).txt`；**只改文件名不改目录**，所以归属仍由落点规则决定（名字变了也不会变成别人的文件）。`跳过` 纯前端，不发请求。
  边界：只在个人空间探同名——共享目录的服务端落点是 `<目录>/<我>/`，前端不复制这套落点规则（复制一份就等着两边漂移），共享目录里覆盖自己的同名文件仍静默发生（D27 认可的代价）。

- **D35 共享目录的双上限：容量 + 成员数，每目录可下调、不可越过全局硬顶**｜`shared_folders` 加两列 `max_bytes` / `max_members`，**0 表示「用全局默认」**（`SUBDRIVE_SHARED_MAX_BYTES` 默认 2 GiB、`SUBDRIVE_SHARED_MAX_MEMBERS` 默认 20，后者硬顶 200）。创建时可选填，之后创建者或管理员可以 `PATCH /api/shared/{id}` 改；填 0 或超过硬顶一律 `400 bad_limit`，不静默截断——上限是防事故的旋钮，不是可以被抬到无意义的装饰。
