# 设置页与「积木式个性化」方案 v1（待拍板，暂未实施）

> 本文只做方案，不动代码。拍板后再按 M1→M4 实施。所有新增设置项都要你先点头才进清单。

## 0. 一句话

把右上角零散的开关（主题、语言、改密码）收进一个全屏设置页；外观部分做成**模块级积木**，
管理员可把整套布置一键推给全员，普通用户只能改自己那份、只影响自己。

## 1. 目标 / 非目标

**目标**

1. 一个入口、一个页面：用户找设置不用猜在哪个图标下。
2. 外观可积木化：7 个模块各自能改颜色/圆角/间距/贴图，整页能换背景与主色，改完立刻生效、刷新还在。
3. 组织能力：管理员一键发布，成员默认继承；成员自己的改动不丢，且能一键回到组织版。
4. 为后续扩展留位：以后加设置项只是往分组里塞一行，不用重排版面。

**非目标（明确不做）**

1. 不做低代码平台：不做自由拖拽画布、不做自定义 HTML/CSS 输入框。
2. 不做国内网盘那套：会员墙、任务中心、皮肤商城、红点促销、设置页里塞运营位——URL 里每多一个「开通」按钮，设置页的可信度就少一分。
3. 不做每像素级自由布局：块只能调顺序/显隐/样式，不能任意定位，否则响应式与移动端会立刻失控。

## 2. 参考与反例

| 来源 | 借鉴什么 | 不借鉴什么 |
|---|---|---|
| DeepTutor | 左侧分组 + 右侧条目式表单；每项一行「标题 + 一句说明 + 控件」；关于页里放版本与依赖 | 它的配置项偏科研，条目太多 |
| Google Drive 设置 | 居中弹窗、分组、**改完即生效没有「保存」按钮**、每项都有「?」解释 | 弹窗高度受限，放不下积木编辑器 |
| OneDrive 设置 | 账户/通知/存储三段的清晰切分；存储页直接给占用明细 | 需要登录态跳转的部分 |
| 夸克 / 百度网盘（**反例**） | — | 设置与营销混排、诱导开通会员、项与项之间塞推荐、关不掉的推送 |

**取舍**：用「全屏二级页 + 左侧锚点导航」，因为积木编辑器需要横向空间；每项即时生效；每项都给一句人话说明。

## 3. 信息架构

`#/settings` 一个视图，左侧 6 个分组，右侧内容区；窄屏折叠成「顶部下拉选分组 + 单列」。

| 分组 | 放什么 | 谁能看 |
|---|---|---|
| 外观与个性化 | 明暗 / 主色 / 语言 / **积木编辑器** / 重置 | 所有人 |
| 账号与安全 | 昵称、改密码、活跃会话*、退出所有设备* | 所有人 |
| 上传与性能 | 上传并发、上传面板行为* | 所有人 |
| 存储与配额 | 用量概览、共享占用明细* | 所有人 |
| 关于 | 版本号、提交哈希、构建时间、许可证、存储模式（stub/live） | 所有人 |
| 站点管理 | 组织布置推送、默认配额、邀请码策略* | 仅管理员 |

带 `*` 的是**待你批准**才做的项（见文末 Q5）。

入口：右上角现有那颗主题按钮升级为「设置」齿轮，点开直接进设置页；头像菜单保留「改名字 / 退出」。
语言下拉移到设置页「外观与个性化」里（顶栏少一个控件，也就不存在宽度漂移问题）。

## 4. 积木式个性化（核心）

### 4.1 块清单（模块级，7 块）

| id | 模块 | 可调 |
|---|---|---|
| `topbar` | 顶栏 | 显示、背景、文字色、高度、贴图 |
| `quota` | 存储条 | 显示、背景、文字色、圆角、贴图 |
| `scope` | 我的网盘 / 公共区域 | 显示、背景、圆角 |
| `toolbar` | 新建 / 上传 / 测速 | 显示、背景、圆角、按钮主色 |
| `shared` | 共享文件夹卡片区 | 显示、背景、卡片圆角、贴图 |
| `files` | 文件列表 | 显示、背景、行高（密度）、斑马纹开关 |
| `foot` | 页脚 | 显示、背景、文字色 |

整页级：`背景色` / `背景图` / `主色` / `字体缩放(0.9–1.15)` / `密度(紧凑/舒适)`。

### 4.2 数据模型

```json
{
  "v": 1,
  "page": { "bg": "#eceef3", "bgImage": null, "accent": "violet", "fontScale": 1, "density": "comfortable" },
  "blocks": [
    { "id": "topbar", "visible": true, "style": { "bg": "#ffffff", "fg": "#16181d", "radius": 0, "padding": 10, "image": null } },
    { "id": "quota",  "visible": true, "style": { "bg": "#ffffff", "fg": "#16181d", "radius": 16, "padding": 16, "image": null } }
  ]
}
```

约束：颜色只接受 `#rrggbb`；数值有上下界（radius 0–28、padding 0–32、fontScale 0.9–1.15）；
`image` 只接受站内图片 id（见 4.5），**不接受任意 URL、不接受 CSS 片段**。

### 4.3 存储与合并

- **组织基线**：服务端表 `org_theme(payload_json, rev, updated_by, updated_at)`，全局一条。
- **用户本地**：`localStorage.subdrive_layout`（含 `baseRev`），只有普通用户改过才存在。
- **渲染规则**：`组织基线` → 逐字段叠加 `用户本地`（用户改过的字段优先；没改过的字段跟随组织）。
- **状态提示**：设置页顶部三种状态——「跟随组织」/「已自定义」/「组织有新版本（采用 / 保留我的）」。
- 这样管理员推送不会抹掉个人改动，个人改动也不会让组织推送失效。

### 4.4 管理员推送

- `PUT /api/admin/theme` 写入 `org_theme` 并把 `rev+1`。
- 成员下次打开页面 `GET /api/theme` 拿到 `rev` 与基线：
  - 从未自定义 → **自动采用**（这就是「一键统一」）；
  - 已自定义 → 顶部横幅「管理员更新了外观」，给「采用 / 保留我的」两个按钮。
- 待拍板（Q2）：要不要允许「强制覆盖」，即连已自定义的用户也直接覆盖。我倾向默认不强制，但给管理员一个勾选框。

### 4.5 贴图

- 用户上传图片 → 存进自己的目录 `_theme/<uuid>.webp`（复用现有上传链路），页面引用 `/api/files/download?path=...`。
- 上限 2 MB，只收 png/jpeg/webp，服务端校验 MIME 与尺寸（≤ 4096px）。
- 不接受外链：一是隐私（会把访问者 IP 泄给第三方），二是离线部署时外链直接裂。

## 5. 技术实现

**后端**（新增很少）

- 表：`org_theme`（一条记录）；端点：`GET /api/theme`（所有登录用户）、`PUT /api/admin/theme`（管理员）、`DELETE /api/admin/theme`（回到默认）。
- 贴图复用 `POST /api/files/upload`，只是目标目录固定在 `_theme`。

**前端**

- 新视图 `#view-settings`，hash 路由 `#/settings`（刷新能回到同一页）。
- 积木编辑器左侧块列表（拖拽排序用原生 `draggable`），右侧实时预览（直接改 CSS 变量，不重建 DOM）。
- 变量命名：`--b-<id>-bg` / `--b-<id>-fg` / `--b-<id>-radius` / `--b-<id>-pad`，挂在 `body` 上；组件样式只引用变量。
- 现有 4 项迁移：主题、主色、语言、改密码；旧 localStorage 键（`subdrive_theme` / `subdrive_accent` / `subdrive_lang`）继续读，保证老用户设置不丢。
- 文案：三份字典各新增约 60 键（zh / hant / en 等长，e2e 会校验）。

## 7. 测试与验收

- e2e 新增约 12 项：进设置页、改主题即时生效、改块色刷新保持、重置、导入坏 JSON 回退、管理员推送后成员看到横幅、采用后生效、非管理员看不到站点管理组。
- 单测：布局 JSON 的 schema 校验（越界值被夹紧）、合并规则（org / user / 缺省三方）。
- 性能：切换布局只写 CSS 变量，实测「改一次颜色到下一帧」< 16ms。

## 8. 风险与回滚

| 风险 | 处理 |
|---|---|
| 布局 JSON 坏数据导致白屏 | 解析失败回退默认 + 设置页永远可达（`#/settings` 不依赖布局） |
| 贴图过大拖慢首屏 | 2 MB 上限 + 服务端压缩到 webp + 懒加载 |
| 管理员误推 | 推送前给全屏预览；保留上一版 rev 可一键回退 |
| 老用户设置丢失 | 旧 localStorage 键只读不删，首次进入设置页自动迁移 |

### 由此确定的实现约束

- 设置页是**独立视图**，不依赖任何布局 JSON：布局坏掉也永远进得去、永远能重置。
- 用户本地布局存 localStorage.subdrive_layout，带 baseRev；服务端只存组织基线 org_theme。
- 合并是**逐字段叠加**，不是整体替换——组织改一处、用户改另一处，两边都保留。
- 贴图只走站内上传链路，页面里引用下载端点，不出现第三方 URL。


## 11. 修订 v1.1：管理员设置与用户设置是**两个面**（按 m02704 的纠正）

第一版方案把「站点管理」当成用户设置里的第六组，这是错的：它会让两种完全不同的职责挤在同一页里——
用户改的是「我自己的网盘长什么样」，管理员改的是「整个部署对所有人意味着什么」。混在一起必然出现
「管理员在用户页里发布组织外观」这种语义错位。

### 两个入口、两套信息架构

| | 用户设置 | 管理员设置 |
|---|---|---|
| 入口 | 右上角齿轮 → 用户设置 | 管理后台页内的「站点设置」 |
| 路由 | /settings | /admin/settings |
| 分组 | 外观与个性化 / 账号与安全 / 上传与性能 / 存储与配额 / 关于 | 组织外观 / 默认值与上限 / 邀请与准入 / 站点信息 / 审计 |
| 能改什么 | 只影响自己（本地布局、自己的密码与昵称） | 只影响整体（组织基线、默认配额、准入策略） |
| 看不到什么 | 任何组织级开关 | 任何「我自己的主题」——管理员要改自己的外观，和普通用户一样走用户设置 |

**共享的只有底层**：布局 schema、主题编辑器组件、org_theme 表与两个端点。页面、文案、权限各自独立。

### 管理员设置首批条目（待逐项批准）

1. 组织外观：编辑一份组织布局 → 预览 → 发布（rev+1）/ 回滚到上一版
2. 默认值与上限：新用户默认配额、共享目录默认容量与成员上限、单文件上限
3. 邀请与准入：邀请码策略（有效期/次数默认值）、是否允许自行注册
4. 站点信息：站点名、Logo、页脚署名人
5. 审计：最近 N 条管理动作（发布主题、改配额、禁用账号）

### 明确不做

- 不在用户设置里放任何「组织」字样；不在管理员设置里放「我的」字样。
- 不允许管理员替某个具体成员改他的本地布局（那是冒充，不是管理）。

| 编号 | 结论 |

| Q9 管理员条目 | 五项全要：组织外观（编辑→预览→发布/回滚）、默认值与上限、邀请与准入、站点信息、审计 |
| Q10 用户条目 | 五项全要：外观与个性化（含积木与重置）、账号与安全（昵称/改密码）、上传并发滑杆、存储用量概览、关于（版本/提交/构建时间/许可证） |
| Q6 主题包 | 要；与管理员发布共用同一份 JSON 格式 |
| Q7 开工范围 | 本轮先做 M1 + M2 |

### 阶段与条目对应（重要：不是所有已批条目都在本轮）

- **本轮 M1**：设置页骨架 + 左侧导航 + 迁移（主题/主色/语言/改密码）+ 用户侧新增：并发滑杆、存储用量概览、关于页；管理员侧「站点设置」子页先立壳 + 默认值与上限、邀请与准入、站点信息、审计（**这四项不依赖布局编辑器**）。
- **本轮 M2**：整页背景/背景图、字体缩放、密度；主题包导出/导入 JSON（本地生效）。
- **下一轮 M3**：积木编辑器（7 块显隐/排序/颜色/圆角/贴图 + 实时预览 + 重置）。
- **下一轮 M4**：组织外观发布（依赖 M3 的编辑器）+ org_theme 表与端点 + 成员横幅/采用 + 回滚。

这样切分的原因：M1/M2 不碰布局数据模型，可以先交付一个能用的设置页；积木与推送是一套新数据模型，
单独一轮才有完整验收面（也就不会出现「设置页做好了但推送是空壳」的中间态）。
